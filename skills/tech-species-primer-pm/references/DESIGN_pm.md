# 业务认知卡 · 基金经理版(v3.3-PM)增量规格

> 本文件是 tech-species-primer-pm 的规格正本之一,只写**相对 v3.2 的增量**。v3.2 的结构、图表密度、MD 写法、视觉规范、数据纪律仍以
> `references/DESIGN_v32.md` 为准;两者冲突时**以本文件为准**。白话写法的细则、类比库和改写正反例在 `references/plain_language_guide.md`。

## 0 为什么要有这一版

2026-09-29 基金经理读完 v3.2 卡片后的反馈(原话):

1. 「主要是少一些用简要通俗的语言来解释技术和技术变化路径的部分,一上来都是专业术语,没有基础背景的人可能比较难读明白。」
2. 「Palantir 那家公司也是一样,没看明白公司业务。」要求在报告里用一段通俗易懂的话把业务讲清楚。

对照 v3.2 的规格和样卡,问题出在结构,不只在措辞:

| 现象 | v3.2 里的原因 | 本版的改法 |
|---|---|---|
| 一上来就是术语 | 公司总览第一段写「本质」,但写法是分析师口吻的定义(「按利润来源看,是一家卖功率变换设备和储能系统的公司」),定义本身就要解释;章首 lead 直接上「定义 + 关键数」 | 新增**零章「一分钟看懂」**放在最前,只用白话、类比和一个真实例子;各业务章 lead 之后加**章首白话块** |
| 技术和技术变化路径没人讲 | 技术内容拆散在各业务章的 x.3 历史演变、x.4 具体产品里,以型号和参数为主;没有一处集中讲「这门技术干什么、怎么一步步变过来」 | 新增**技术白话章**(五节固定),必有一张**技术路线图**(roadmap 块:每一代解决了什么、代价、谁受益谁受损、下一步分岔) |
| 术语首现有白话只是口号 | 铁律第 11 条写了,但没有验收;名词表放在最后一章,读者读到时已经放弃 | 各章写**术语台账 NN_terms.md**,合成词典;正文里每章第一次出现的术语**悬停即见白话解释**;`--pm` 验收查英文缩写首现有没有解释 |
| 平台型公司(Palantir)读不懂 | 产品名(Gotham / Foundry / Apollo / AIP)和概念(Ontology)本身就是黑话;没有类比、没有客户前后对比,读者脑子里形成不了画面 | 零章强制「打个比方」与「举个例子」(真实客户,前后对比),另加「是什么、不是什么」表,把读者最容易套错的类比(数据库?咨询?大模型?)先排除 |

读者画像:**基金经理**,懂财务报表、估值和行业比较,不懂这门技术;先花五分钟决定要不要往下读;读完要能向投委会或领导复述。
所以全卡分三层,读者可以在任一层停下:

1. **白话层**(约 5 分钟):零章 + 各章章首白话块 + 技术白话章的路线图。只用白话、类比、例子和少量取整后的数。
2. **结构层**:各章 lead、图题(写结论)、表。
3. **证据层**:v3.2 原有的全部正文、图表、来源与口径。

## 2 零章「一分钟看懂」

**位置**:页头 meta 盒之后的第一章,章号「零」,目录分组「先看这里」。**由主线在所有业务章写完、数字底座定稿后最后写**,章节 agent 不写本章。
**篇幅**:汉字 500–1,800(含表);英文缩写 ≤3 个(公司名、代码、读者熟知的词不算);数字 ≤5 个,全部来自数字底座,写成「约四分之三」「翻了一倍」这类说法。
**固定六块**(顺序不变,每块开头的小标题保留):

| 块 | MD | 写什么 | 不许写什么 |
|---|---|---|---|
| 一句话 | `> [!lead] **一句话:…**` | ≤60 字:卖什么东西、帮谁解决什么问题;再一句交代客户是谁 | 术语、产品型号、「领先的」「平台型」这类形容 |
| 打个比方 | `> [!plain] 打个比方:…` | 用读者天天见的东西类比;先讲客户原来的麻烦,再讲产品怎么解决;点明类比在哪里不成立;最后把公司自己的叫法对上 | 为类比而类比;一段里两个以上比喻 |
| 举个例子 | `> [!example] 举个例子:…` | 一个真实客户或场景,写成前后对比(以前怎么做、花多久;现在怎么做、改善了什么),有出处 | 编造或虚构客户;把厂商宣称写成事实(要标〔厂商口径〕) |
| 钱怎么来 | `> [!plain] 钱怎么来:…` | 谁付钱、按什么收费、为什么重复买;收入最大的一块;成本大头在哪 | 估值、目标价、盈利预测 |
| 技术怎么变 | `> [!plain] 技术怎么变:…` | 3–5 步,每步一句「解决了上一代什么麻烦」;指向技术白话章 | 型号清单 |
| 要盯的一件事 | `> [!plain] 要盯的一件事:…` | 最关键的一个不确定性,写成「看什么数、什么时候能看到」 | 买卖建议 |

另加两样:**表 0-1「是什么、不是什么」**(3–5 行:读者最容易套错的类比 → 实际情况 → 更接近哪一类);**图 0-1「钱怎么流」**(chain 块:谁付钱、公司从哪买、卖给谁、最终用在哪)。
骨架:`assets/templates/ch00_plain.md`;正例:`examples/pm/pltr_plain_sample.md` 零章(平台软件)、`examples/pm/cpo_tech_path_sample.md` 零章(产业链)。

## 3 技术白话章

**目标**:没有工程背景的读者读完,能复述「这门技术解决什么问题、原理一句话、一代代怎么变过来、下一步往哪几个方向分岔、对公司意味着什么」。
**篇幅**:汉字 1,500–2,800;图 ≥3(原理示意 1、路线图 1、代际对比表不算图但必有);由一个章节 agent 在数字底座建好后写。
**五节**(节名可改写成结论句,但不许用「行业规模 / 竞争格局 / 具体产品 / 核心竞争」这几个词):

1. **x.1 它要解决的问题**:先讲客户(或客户的客户)遇到的麻烦,再讲旧办法为什么不够;加一个 `[!plain] 打个比方`。
2. **x.2 原理:一张图看懂**:flow 块(按信号 / 物料 / 数据走的顺序)或 chain 块(分层),图题含「原理」;标出下一代技术要改动的环节(hot)。图后一段:哪几个环节决定成本和性能。
3. **x.3 演进路线**:**roadmap 块必放**(3–6 代;每代 era / name / gist / solves / cost / who;当前主力标 now,未量产标 future;fork 写 2–3 个方向,各写赢的条件与看什么信号)+ 表「各代技术的白话对比」。
4. **x.4 下一步的分岔与验证信号**:不下结论,只给判别方法与大致时间。
5. **x.5 对公司意味着什么**:技术变化怎么传导到公司卖的东西(量、价、形态)、份额与话语权、成本与毛利率;指向后面业务章。以一个 `[!plain] 对投资意味着什么` 收尾。

参数只保留读者判断需要的数量级(「十几厘米 vs 几毫米」「几个月 vs 5 天」),精确参数留在业务章 x.4 具体产品。
骨架:`assets/templates/ch_tech_plain.md`;正例:两份 `examples/pm/` 样例的第二章。

## 4 全卡白话纪律

1. **业务章章首白话块**:每个主业章在 `[!lead]` 之后、第一个 `###` 之前放一个 `> [!plain] 白话:…`(≤200 字):这块业务用大白话讲是什么、打个比方或举个例子、看这块业务关键看什么数。验收硬查。
2. **每节第一句是白话结论**,再上图和数据(评审 C 抽查,不进自动验收)。
3. **术语**:首现当场用一句白话解释,格式「中文名(英文缩写,一句白话)」或「英文名(中文名)」+ 下一句解释;不许用术语解释术语;每段新出现的术语 ≤2 个。每章把本章首现的术语登记到 `parts/NN_terms.md`(表头 `| 术语 | 白话解释 | 打个比方 | 对投资意味着什么 |`,别名用「 / 」分隔),`merge_card.py` 合成「附录、术语小词典」。正文里每章第一次出现的词典术语自动加虚线下划线,悬停或点按显示白话解释。
4. **类比**:只在零章、章首白话块、技术白话章 x.1 用;每处 1 个。好类比三条件:读者熟悉、结构对得上、说清边界(「不同的是……」)。正文证据层仍按 v3.2「少比喻」。
5. **例子**:真实、前后对比、有出处;厂商宣称标〔厂商口径〕,媒体报道标〔公开报道〕。
6. **数字**:白话层用取整和倍数说法;精确值、口径、页码留在证据层;两层的数必须能对上(白话层的「约四分之三」对应证据层的 74.2%)。
7. **图题**:仍写结论,但用白话写(「光器件一步步往芯片靠,省电越多、维修越难」,不写「CPO 功耗 pJ/bit 对比」)。
8. 白话不是营销腔:不许夸张、不许比数据说得满;「赋能」「一站式」「颠覆」照旧禁用。

## 7 评审 C:外行复述评审

在评审 A(版式深度)、评审 B(数字核对)之外加一路:子代理扮演「懂财务、不懂这门技术的基金经理」,**只读白话层**(零章、各章 lead 与白话块、技术白话章),不看证据层,用自己的话复述五件事(卖什么、卖给谁、怎么赚钱、技术怎么变、最该盯什么),并逐条列出卡住的词和句。主线对照原文判定复述「对 / 偏 / 错」;有「错」或卡住的词 >5 个,改白话层后重评。协议见 `references/review_protocol.md` §3,记录写 `work/reader_test.md`,结论进评审处理记录。
