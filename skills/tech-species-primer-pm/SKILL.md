# 业务认知卡 · 基金经理版 v3.3-PM

> 本 skill 由 tech-species-primer v3.2.0 派生,**v3.2 的全部规格、脚本、数据纪律照旧有效**(`references/DESIGN_v32.md`),
> 本版只在上面加一层通俗解释(`references/DESIGN_pm.md`,两者冲突时以 PM 为准)。写法细则、类比库、竞品对比写法、改写正反例在
> `references/plain_language_guide.md`;完整写法样例在 `examples/pm/`(Palantir 业务与「和普通 SaaS 的区别」、CPO 技术路径与「和可插拔、NPO 的区别」)。

## 它做什么

读者是**基金经理**:懂财务报表、估值和行业比较,**不懂这门技术**;先花五分钟决定要不要往下读,读完要能向投委会或领导复述。
读完要能讲清:**业务本质、客户与付费方、价值流向、与同类产品的差异、技术演变与下一阶段的可能路径、跟踪指标**。

基金经理的反馈(2026-09-29,两轮)与本版的对应改法:

| 反馈 | 本版改法 |
|---|---|
| 「一上来都是专业术语,没有基础背景的人比较难读明白;少了用通俗语言解释技术和技术变化路径的部分」 | 最前面加**零、业务速览**;加技术章**「技术与产品:原理、差异与演变」**,核心是一张**技术演变路线图**(每一代解决的问题、代价、受益与受损方、下一阶段的可能路径);每个业务章开头加一段**通俗解释**;术语进**词典**并在正文**悬停即见解释**;`--pm` 验收查缩写首现有没有解释 |
| 「Palantir 没看明白公司业务,要用一段通俗易懂的话把业务讲清楚」 | 零章要有加粗的一句话定位、关键数据、类比、真实客户的前后对比、价值流向与价值流向图;样例见 `examples/pm/pltr_plain_sample.md` |
| 「『白话』这样的标签不要直接写上去,重新排版」 | 类比与案例用块类型区分底色,**页面上不出现任何写作标签**;验收查标签外露 |
| 「还要说清楚和竞品的区别:Palantir 和普通 SaaS、CPO 和可插拔、和 NPO」 | 零章与技术章各有**「与 XX 的差异」**一节:先分类 → 结构对比图 → 每对相邻方案一段(差异 + 收益 + 代价)→ 逐项对比表 → 投资含义;验收硬查 |
| 「第 0 部分格式还不好看,要改 UI;AI 化的表述要更买方,『钱往哪里流』『技术怎么一步步变过来』改成『价值流向』『技术演变』」 | 零章改成**速览版式**:摘要面板(定位 + 关键数据分栏)+ 带序号的卡片网格(含表或图的卡片占整行);小标题改用买方用语(与 XX 的差异 / 工作原理 / 客户案例 / 价值流向 / 技术演变 / 跟踪指标);正文按 buyside-voice 的 voice-rules 写;`--pm` 查口语化、问句式表述 |
| 「人理解新技术要和来源或老一代技术对比,Palantir 可以和 SaaS 对比;用大白话讲明产品工作原理,再放一张产品图,图不需要再用文字讲解」 | 零章**先比后讲**:第一张卡片固定是「与前代 / 同类方案的差异」,第二张「工作原理」一段通俗说明后直接放**产品图**(官网 / 发布会 / 研报原图优先,拿不到时自绘示意并注明),图下不写解释;`--pm` 查对比节是否在首位、零章是否有产品图 |

全卡分三层,读者可在任一层停下(层是写作概念,页面上不出现层名):**通俗层**(零章 + 各章开头的通俗解释 + 技术章的对比图表与路线图,约 5 分钟)→ **结构层**(lead、图题、表)→ **证据层**(v3.2 的全部正文与来源口径)。
只建认知,不做估值、不给买卖建议。

| 对象 | 章节主干 |
|---|---|
| 公司卡 | **零、业务速览** → 一、公司总览 → **二、技术与产品:原理、差异与演变** → 每个主业一章(lead + **通俗解释** + 六节)→ 专题章 → 非主业 → UE与经营效率 → 跟什么走 → 正在变什么 → 来源与口径 → **附录、术语小词典** |
| 主题卡 | 同上,零章与技术章只讲主题业务;非主题业务一章简述 |
| 产业链 / 技术物种卡 | **零、业务速览** → **一、技术解析:原理、方案差异与演变路线**(吸收 v3.2 的是什么 / 为什么是现在 / 路线之争)→ 产业链每一环一章(通俗解释 + 六节)→ 谁付钱 → 对现有产业链意味着什么 → 跟什么走 → 正在变什么 → 来源与口径 → **附录、术语小词典** |

技术不是看点的公司(品牌消费、渠道、金融),经用户同意可不设技术章(`--no-tech`),在相应业务章 x.3 开头写一段演变说明;零章的「与 XX 的差异」仍要写(比商业模式)。

## 铁律(违反即返工)

1–12 条沿用 v3.2:

1. **从 0 开始**:旧卡、旧一页纸的结论、章题、数字不沿用;本地材料只作线索,每个数回原文核对。**用户已有文件只读。**
2. **数字回一手**:公司数回招股书 / 年报 / 10-K 原页,全卡写 **PDF 页码**;行业数写机构、报告日期、页码;缺的写「数据不可得」并写清查过哪些文件。
3. **先建统一数字底座**(`work/facts_spine.md`),全卡同一个数前后一致;多套口径并存时分开列,每张图写明用哪套。
4. **口径冲突并列**:图后 `> [!note] 口径分歧:…`,同时进来源与口径章的取舍表。
5. **不写**估值、目标价、评级、PE/PS、卖方盈利预测;卖方观点只能以〔卖方估计〕进叙述;含这些内容的研报原图整张不用。
6. **不照抄参考报告**:`--gate --ref` 的照抄检查必须 0 命中。
7. **图多但不堆**:目标 55–70 张,每张一句话说清它证明什么;同一信息不重复出图。
8. **图片进卡前用 Read 看一眼**;alt 带类别前缀;不收签约、剪彩、展会、合影照片。
9. **取数纪律**:Wind 一张卡最多 1 次、结果落盘;iFind 不用;FMP 只定点;AlphaPai 只用 `image`。
10. **隐私**:任何网络请求不带用户邮箱;EDGAR 用 `curl --noproxy '*'` 与非个人 User-Agent。
11. **写法**:中文为主;叙述为主,判断先行、证据跟上、推理看得见;段内加粗 1–3 处;标题即结论且不比数据说得满;不写空话;「锚定」改用「对照」。语言规范以 buyside-voice 的 `references/voice-rules.md` 为准(破折号 ≤8、判断性警句 ≤8 且只放结论位、禁词、三档语气、明示不确定),本 skill 不复制;本机装有 buyside-voice 时交付前对合并后的 MD 跑 `scripts/voice_scan.py`。
12. **交付前验收**:`merge_card.py` 通过(退出码 0)→ 三路评审处理完 → `shots.py` 截图无 JS 报错、无坏图、手机宽无横向溢出。

基金经理版另加:

13. **通俗先行**:零章在最前;每个业务章 lead 之后、第一个 `###` 之前有一段通俗解释(`[!plain]` / `[!analogy]` / `[!example]` 块);每节第一句是通俗的结论。
14. **技术讲路径,不讲型号**:技术章必有 roadmap 路线图,每一代写清「解决了上一代什么麻烦、代价是什么、谁受益谁受损」,最后给下一步分岔与验证信号。
15. **先比后讲,讲清与竞品的差异**:零章第一张卡片是「与 XX 的差异」,之后才讲工作原理并配产品图(图下不写解释);技术章另有「与 XX 的差异」一节;对比对象选读者熟悉的那一类(Palantir → 普通 SaaS;CPO → 可插拔与 NPO);先分类、再画结构对比图、每对方案写差异与代价、最后逐项对比表。只写差异不写优劣,每个优点写出代价。
16. **术语不裸奔**:首现当场一句话解释(不许用术语解释术语),每段新术语 ≤2 个;每章登记 `parts/NN_terms.md`,合成词典、正文悬停释义。
17. **类比与例子有纪律**:类比只放在零章、各章开头的通俗解释、技术章 x.1,每处一个,说清边界;例子必须真实、前后对比、有出处,厂商宣称标〔厂商口径〕。通俗不是营销腔,不许比数据说得满。
18. **页面上不写写作标签**:正文、标题、图题不出现「白话」「一句话:」「打个比方:」「举个例子:」这类字样;分块用小标题或块类型(只改底色)。
19. **买方用语**:不写口语化、问句式表述(「钱怎么来 / 钱往哪里流」「技术怎么一步步变过来」「最该盯的一件事」「它像什么」「有什么不同」「是怎么回事、往哪走」),改用「价值流向」「技术演变」「跟踪指标」「业务本质」「与 XX 的差异」「技术与产品 / 技术解析」;对照表见 `plain_language_guide.md` §6,`--pm` 会报。

## 流程

**第 0 步 · 立项与建目录**
- 实体消歧(上市主体、运营主体、口径主体、代码与币种);主题卡 / 产业链卡把范围写死。
- `python3 $S/scripts/new_card.py --root R --name 宏和科技 --code 603256.SH [--type company|theme|industry] [--no-tech]`
- 用户给了完整 prompt 就原文存 `work/PLAN.md`;没给就按 `references/kickoff_prompt_template.md` 写一份(含基金经理版要求),给用户过目再开工。
  写 PLAN 时先回答一个问题:**这家公司最容易被读者套错成哪一类生意?**(答案进零章「是什么、不是什么」表。)

**第 1 步 · 盘点材料,先落盘 `materials.md` 与 `questions.md`**(同 v3.2)
- 一手文件按市场取(`references/data_sources.md`);PDF 用 `scripts/pdf2txt.py` 转按页文本;招股书与年报的图用 `scripts/pdfimg_catalog.py`;研报原图 `scripts/ap_images.py`。
- 20–35 个必答问题里,**至少 6 个是通俗层的问题**(「用一句话说它卖什么」「客户原来怎么解决这个问题」「读者最常拿它和什么比较、差异在哪」「技术每一代解决了什么」「最真实的一个客户案例是什么」「读者最容易误解成什么」),标到零章或技术章。
- 另找 **2–3 个真实客户案例**(官网案例、客户公告、业绩会、招股书)、**技术代际材料**(厂商发布、标准组织文件、研报的技术路线图)与**替代方案材料**(同类产品的定价与交付方式、替代技术的结构与量产状态),作为零章例子、对比节和路线图的证据。

**第 2 步 · 数字底座 `work/facts_spine.md`**(同 v3.2,`references/facts_spine_template.md`)

**第 3 步 · 改 `work/BRIEF.md`**(new_card.py 已按 `references/BRIEF_template.md` 填好路径,含基金经理版 §2b 与 §5b)
- 补 §0 读者目标、§1 材料表、§3 业务章清单;样例 `examples/dekeli/BRIEF.md`。

**第 4 步 · 按章并行写 `parts/`**
- workflow(用户说 ultracode 或同意时)或 Agent 子代理,每章一个 agent;任务里写:章号与章名、必读 BRIEF 与 `references/plain_language_guide.md`、
  本章 questions 编号、图数 / 表数 / 字数目标、必放图类,以及**章首通俗解释与 `NN_terms.md`**。
- **技术章单独一个 agent**,按 `assets/templates/ch_tech_plain.md` 与 DESIGN_pm §3 写(含「与替代方案的差异」一节),必读两份 `examples/pm/` 样例的技术章。
- 子代理回主线 ≤300 字(章号、图数、表数、字数、通俗解释块数、登记术语数、错误数、主要缺口)。

**第 5 步 · 主线写零章「业务速览」**(所有业务章与技术章落盘之后)
- 按 `assets/templates/ch00_plain.md` 与 DESIGN_pm §2 写 `parts/00_业务速览.md`:加粗 lead + `kpis` 关键数据(渲染为摘要面板)+ 六个小节,**先比后讲**(与 XX 的差异 + 表 0-1 / 工作原理 + 产品图 / 客户案例 / 价值流向 + 图 0-1 / 技术演变 + 时间轴 / 跟踪指标,渲染为编号卡片);产品图按官网 → 发布会 → 招股书 → 研报原图 → 自绘示意的顺序取,图下不写解释;用语照 `plain_language_guide.md` §6,页面上不写标签字样。
- 数字只从底座取、取整;例子用第 1 步找到的真实案例;写完删掉所有 TODO。

**第 6 步 · 合并渲染与验收**
- 按最终章节改 `card.json` 的 `nav`、`ref_bg`、`plain.allow`(公司英文名、代码);`work/00_header.md` 的口径与底稿两行写实。
- `python3 $S/scripts/merge_card.py --root R` → 合并(自动由 `NN_terms.md` 合成术语词典)、渲染、`--gate --pm`。看汇总行、
  「基金经理版:」一行与未达标项,补缺直到退出码 0。只看输出尾部,不打印整份 HTML。

**第 7 步 · 三路评审**(`references/review_protocol.md`)
- 评审 A(版式、深度、重复出图)、评审 B(抽 50+ 个数回原文,专查口径混用)同 v3.2;
- **评审 C(外行复述)**:子代理扮演不懂技术的基金经理,只读通俗层,复述六件事(含「与同类产品的差异」)并列出卡住的词句、像模板标签或口语化的表述;记录写 `work/reader_test.md`。复述有「错」或卡住的地方 >5 处,改通俗层后换新子代理重评。
- 按意见修正(改前备份 `_bak_rN/`),重跑第 6 步;写 `评审处理记录.md`(结果表 / 评审 A / 评审 B / 评审 C / 仍有的局限)。

**第 8 步 · 截图验版式**
- `python3 $S/scripts/shots.py --root R`,Read 逐张看;另看一张零章首屏、一张路线图、一张术语悬停。验收同 v3.2。

**第 9 步 · 交付**
- 文件:MD、HTML、materials.md、评审处理记录.md(含评审 C 的复述结果)。
- `merge_card.py --feishu` 另存「{公司}科普-基金经理版-YYMMDD.html」,经用户同意后传飞书云空间根目录。
- 一句话报:图数(交互 / 图片 / 自绘)、表数、汉字数(渲染器口径与纯叙述)、通俗解释块数、词典条数、评审 C 结论、数据缺口。

## 已有 v3.2 卡片改成基金经理版(例:Palantir)

v3.2 卡片的证据层(数字、图表、来源口径)可以保留,只补通俗层,不必从 0 重做:

   `out_stem` / `feishu_name` 改成基金经理版命名;parts 章号整体后移,空出 `00`(零章)和 `02`(技术章)。

## 结构与门槛速查

- **v3.2 门槛不变**(`references/DESIGN_v32.md` §3/§6):图 ≥55(交互 ≥30、原图 / 流程 / 示意等 ≥20)、表 ≥10、汉字 ≥10,000(**术语词典不计入**)、业务章六节与必放图、每张图表有来源行、照抄检查 0 命中。
- **基金经理版门槛**(`--pm`,DESIGN_pm §5):零章在最前、汉字 500–2,200、第一个小节是「与 XX 的差异」对比节(含表)、有工作原理与产品图、有案例、英文缩写 ≤3;技术章有 roadmap 与对比节(含表);每个业务章开头有通俗解释块;词典 ≥15 条;首现无解释的英文缩写 ≤3;页面上无写作标签、无口语化表述;无残留 TODO。门槛在 card.json `plain` 里改(下调须用户同意)。
- **新 MD 语法**:`> [!plain] …`、`> [!analogy] …`、`> [!example] …`(页面不显示标签,只改底色)、```` ```roadmap {JSON} ````、flow 块 `lanes` 画方案结构对比、```` ```glossary 术语 | 是什么 | 可以理解成 | 对投资意味着什么 ````;样例在 `assets/fixture/fixture.md` 末节与 `examples/pm/`。
- 专题章、技术章的 h3 不用「行业规模 / 竞争格局 / 具体产品 / 核心竞争」(否则按业务章验收)。

## 上下文预算(主线 ≤18%)

- 主线只做:读规格、写 PLAN / materials / questions / BRIEF、建底座、编排子代理、**写零章**、合并渲染、汇总评审、交付。取证、下载、写章、看图、评审全放子代理。

- 接近 18% 时按「底座 → 各章落盘 → 零章 → 合并 → gate 通过 → 飞书」的顺序保。
